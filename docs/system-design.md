## 1. الملخص التنفيذي

**الهدف:** بناء منصة رقمية واحدة لمحل **غصن** (تجهيز وتغليف الهدايا، مستلزمات الهدايا، العطور، الملبوسات النسائية، أدوات التجميل) تجمع بين إدارة المحل الفعلي والمتجر الإلكتروني على **مخزون واحد وقاعدة بيانات واحدة**.

**القرار المعماري:** نظام مخصص (Custom) من ثلاث واجهات فوق خلفية (Backend) واحدة:

1. **لوحة الإدارة (Admin):** المنتجات، المخزون، المشتريات، العملاء، المالية، التقارير.
2. **نقطة البيع (POS):** تطبيق ويب يعمل على جهاز لوحي/لابتوب، ويستمر في البيع عند انقطاع الإنترنت ثم يزامن.
3. **المتجر الإلكتروني (Storefront):** عربي أولاً، سريع على شبكات الجوال الضعيفة، مع دفع عبر بنكك أو عند الاستلام أو إرسال الطلب عبر واتساب.

**+ تطبيقات جوال:** تطبيق للعملاء وتطبيق للموظفين (المالك، المدير، المغلّف، المندوب) فوق نفس الـAPI — التفاصيل في القسم 11.

**لماذا نظام مخصص وليس منصة جاهزة؟**

- معظم المنصات العالمية (Shopify، Stripe، وغيرها) لا تدعم السودان كبلد تاجر أو لا تدعم وسائل الدفع المحلية.
- نشاط "تجهيز الهدايا" يحتاج منطقاً خاصاً (هدية = مكونات + مواد تغليف + خدمة + بطاقة إهداء + موعد تسليم) لا توفره المنصات الجاهزة بشكل جيد.
- تذبذب سعر الجنيه يتطلب تسعيراً مرتبطاً بتكلفة الاستيراد وسعر الصرف.
- تكلفة تشغيل شهرية منخفضة وملكية كاملة للبيانات.

**النطاق:** فرع واحد عند الإطلاق، مع تصميم يدعم تعدد الفروع والمخازن لاحقاً دون إعادة بناء.

## 2. المتطلبات والافتراضات

### 2.1 المتطلبات الوظيفية

| المجال | المتطلب |
|---|---|
| المنتجات | أصناف بمتغيرات (مقاس/لون/حجم عطر)، باركود، صور، سعر بيع وتكلفة، تاريخ صلاحية للعطور ومستحضرات التجميل |
| الهدايا | بكجات جاهزة (Bundles) + هدايا مخصصة يختار العميل مكوناتها ونوع التغليف وبطاقة الإهداء، مع خصم مواد التغليف من المخزون |
| البيع بالمحل | POS سريع، خصومات، دفع متعدد (كاش + بنكك)، مرتجعات واستبدال، إيصال حراري أو عبر واتساب، فتح/إغلاق وردية |
| المتجر | تصفح، بحث، سلة، إتمام طلب بدون تسجيل (برقم الهاتف)، تتبع الطلب، 4 طرق إتمام |
| المخزون | رصيد لحظي موحد، حجز الكمية للطلبات الأونلاين، تنبيه حد إعادة الطلب، جرد، تالف |
| المشتريات | موردون، أوامر شراء، استلام، **تكلفة وصول (Landed Cost)** تشمل الشحن والجمارك |
| العملاء | سجل برقم الهاتف، سجل مشتريات، مناسبات (أعياد ميلاد/زواج) للتسويق، نقاط ولاء (مرحلة 2) |
| المالية | مصروفات، صندوق وحساب بنكك، أرباح حسب الصنف والفترة |
| الصلاحيات | مالك، مدير، كاشير، مغلّف، مندوب توصيل |

### 2.2 المتطلبات غير الوظيفية

- **العمل دون إنترنت:** الـPOS يبيع محلياً ويزامن عند عودة الاتصال.
- **الأداء:** صفحات المتجر أقل من 300KB للتحميل الأول، صور WebP مضغوطة، تعمل على 3G.
- **اللغة:** عربي (RTL) افتراضي، إنجليزي اختياري.
- **التوسع:** حقل `branch_id` و`warehouse_id` في كل حركة من اليوم الأول.
- **قابلية التدقيق:** كل تعديل على المخزون أو الأسعار أو المبالغ يُسجّل بالمستخدم والوقت.

### 2.3 افتراضات بيئة السودان (تحتاج تأكيدك)

1. الإنترنت والكهرباء غير مستقرين ← يلزم UPS للجهاز وراوتر بشريحتين من مزودين مختلفين (مثلاً زين + MTN).
2. **بنكك لا يوفر بوابة دفع (API) عامة للتجار — حسب ما هو معروف حتى الآن، ويجب التحقق مع بنك الخرطوم.** لذلك التصميم يعتمد على التحويل اليدوي + رفع إشعار + تأكيد موظف، مع طبقة `PaymentProvider` تسمح بإضافة بوابة إلكترونية لاحقاً.
3. البضاعة مستوردة بعملات أجنبية (درهم/دولار/جنيه مصري) وتُباع بالجنيه السوداني ← نظام أسعار صرف وإعادة تسعير.
4. التواصل الأساسي مع العملاء عبر واتساب، والعناوين وصفية (حي + معلم) وليست بريدية ← الحقل الأساسي هو الهاتف + الحي + وصف + موقع خريطة اختياري.
5. الاستضافة خارج السودان وتُدفع ببطاقة دولية (من قطر).

## 3. المعمارية التقنية

### 3.1 الصورة العامة

```
[المتجر - Next.js SSR]   [لوحة الإدارة]   [POS - PWA Offline]
            \                  |                   /
             \                 |                  /
              +---- API موحدة (Next.js Route Handlers / tRPC) ----+
                               |
        PostgreSQL  +  تخزين صور (Cloudflare R2)  +  Jobs (النسخ الاحتياطي، التنبيهات)
                               |
                 واتساب (wa.me ثم Cloud API)  ← إشعارات الطلبات
```

**مبدأ أساسي:** تطبيق واحد (Modular Monolith) وليس Microservices — مطوّر واحد يستطيع صيانته، والوحدات مفصولة داخلياً (catalog, inventory, sales, orders, gifts, finance) بحيث يمكن فصلها لاحقاً.

### 3.2 التقنيات المقترحة

| الطبقة | الاختيار | السبب |
|---|---|---|
| الإطار | Next.js (TypeScript) | متجر SSR سريع ومؤهل لمحركات البحث + لوحة إدارة + POS في مشروع واحد |
| قاعدة البيانات | PostgreSQL + Prisma | معاملات (Transactions) موثوقة للمخزون والمال |
| واجهة المستخدم | Tailwind + shadcn/ui (RTL) | تطوير سريع ومكوّنات جاهزة |
| POS Offline | PWA + IndexedDB (Dexie) + طابور مزامنة | يعمل من المتصفح دون تثبيت |
| المصادقة | Auth.js / Better Auth + أدوار | موظفون بكلمة مرور، عملاء بـ OTP عبر واتساب (مرحلة 2) |
| الصور | Cloudflare R2 + تحويل WebP | تكلفة شبه معدومة وبدون رسوم نقل |
| الاستضافة | VPS (Hetzner أو DigitalOcean) + Docker + Coolify | تكلفة ثابتة منخفضة، نشر بضغطة |
| CDN/حماية | Cloudflare | تسريع وحماية DDoS وشهادة SSL مجانًا |

### 3.3 مقارنة البدائل

| البديل | المزايا | العيوب | الحكم |
|---|---|---|---|
| **Next.js + PostgreSQL** | كود واحد لكل شيء، PWA أصيلة، أداء متجر ممتاز | لوحة الإدارة تُبنى يدوياً | **الموصى به** |
| Laravel + Filament | لوحة إدارة جاهزة سريعة جداً | الـPOS Offline يحتاج تطبيق JS منفصل | بديل قوي |
| Odoo Community | وحدات جاهزة كثيرة | ثقيل، تخصيص الهدايا والمتجر العربي مكلف | غير مناسب لحجمك |
| WooCommerce | متجر سريع | POS ومخزون ضعيفان، إضافات مدفوعة كثيرة | لا |

> **قرار معتمد:** Basil هو المطوّر والمسؤول عن الصيانة (لا اعتماد على مطوّر محلي) → التقنية المعتمدة: **Next.js + PostgreSQL**. ولأن المطوّر شخص واحد، تُضاف ضمانات: اختبارات تلقائية لمنطق المخزون والمال، CI/CD من GitHub ينشر تلقائياً، بيئة Staging منفصلة، مراقبة أخطاء (Sentry)، ودليل تشغيل (Runbook) للاستعادة والنشر — حتى يبقى النظام قابلاً للإدارة عن بُعد من قطر دون تدخل يدوي في السودان.

### 3.4 النطاقات (Domains) — معتمد

| النطاق | الاستخدام |
|---|---|
| `ghusn.store` | **النطاق الرئيسي** — المتجر الإلكتروني |
| `admin.ghusn.store` | لوحة الإدارة |
| `pos.ghusn.store` | نقطة البيع |
| `api.ghusn.store` | الـAPI (التطبيقات وWebhook واتساب) |
| `media.ghusn.store` | الصور عبر Cloudflare R2 |
| `staging.ghusn.store` | بيئة الاختبار |
| `info@ghusn.store` | البريد الرسمي |
| `ghusn.app` (اختياري) | يُسجَّل للحماية ويحوّل إلى `ghusn.store` |

- التسجيل عبر Cloudflare Registrar أو Namecheap، باسم Basil، مع التجديد التلقائي والتحقق الثنائي.
- **تنبيه:** امتداد `.store` غالباً رخيص في السنة الأولى وأغلى عند التجديد — تحقق من سعر التجديد قبل الشراء، ويمكن الدفع لعدة سنوات مقدماً.
- معرّفا التطبيقين: `store.ghusn.app` (العملاء) و`store.ghusn.staff` (الموظفين).

## 4. وحدات نظام إدارة المحل

### 4.1 الكتالوج (Catalog)

- تصنيفات شجرية: هدايا جاهزة / مستلزمات هدايا / عطور / ملبوسات نسائية / تجميل / **مواد تغليف (داخلية، غير معروضة للبيع)**.
- المنتج (Product) ← متغيرات (Variants): المقاس، اللون، الحجم (50ml/100ml). المخزون والباركود والسعر على مستوى المتغير (SKU).
- توليد باركود داخلي وطباعة ملصقات للأصناف التي بدون باركود.
- نوع الصنف: `stock` (مخزوني) / `service` (خدمة تغليف) / `bundle` (بكج من مكونات) / `material` (مادة تغليف مستهلكة).

### 4.2 وحدة الهدايا والتغليف (الميزة التنافسية)

- **بكجات جاهزة:** كل بكج له وصفة (BOM) — مثال: "بكج عروس" = عطر + بخور + صندوق خشبي + 2م شريط + بطاقة. عند البيع تُخصم المكونات تلقائياً.
- **الهدية المخصصة (Gift Builder):** العميل يختار المنتجات + نمط التغليف (عادي/فاخر/صندوق) + نص البطاقة + اسم وهاتف المستلم + موعد التسليم.
- **نمط التغليف (Wrap Style):** له سعر خدمة + قائمة مواد مستهلكة قياسية ← تحسب تكلفة وربح التغليف بدقة.
- **لوحة المغلّف (Wrapping Queue):** طلبات بالحالة (جديد ← قيد التجهيز ← جاهز ← تم التسليم) مرتبة حسب موعد التسليم، مع رفع صورة الهدية النهائية وإرسالها للعميل.
- المواد بوحدات قياس مختلفة (متر شريط، ورقة، حبة) مع تحويل (لفة شريط = 25م).

### 4.3 المخزون

- المخزون = مجموع حركات (Stock Ledger) وليس رقماً يُعدّل مباشرة — كل تغيير له مصدر (شراء، بيع، مرتجع، تالف، جرد، تحويل).
- حجز (Reservation) للطلبات الأونلاين غير المدفوعة مع انتهاء تلقائي (مثلاً 24 ساعة).
- تتبع دفعات وتواريخ صلاحية (Batches) للعطور والتجميل مع صرف الأقرب انتهاءً (FEFO) وتنبيه قبل 90 يوماً.
- جرد دوري وجزئي (Cycle Count) بالمسح الضوئي، وتقرير فروقات.
- طريقة التكلفة: **المتوسط المرجّح (Weighted Average)** — الأبسط والأنسب لبضاعة بدفعات متكررة بأسعار مختلفة.

### 4.4 المشتريات والموردون

- موردون (دبي، مصر، محلي) بعملة كل مورد.
- أمر شراء ← استلام (جزئي/كامل) ← فاتورة مورد ← مدفوعات.
- **تكلفة الوصول:** إضافة مصاريف الشحنة (شحن، جمارك، تخليص، نقل داخلي) وتوزيعها على الأصناف حسب القيمة أو الكمية ← تكلفة حقيقية بالجنيه.
- اقتراح سعر بيع = تكلفة الوصول × (1 + هامش التصنيف)، مع تقرير "أصناف يجب إعادة تسعيرها" عند تغيّر سعر الصرف بأكثر من نسبة محددة.

### 4.5 نقطة البيع (POS)

- مسح باركود / بحث / شبكة أصناف سريعة بالصور.
- خصم على الصنف أو الفاتورة (بحد أقصى حسب الدور، وما فوقه يحتاج رمز مدير).
- دفع مجزأ: كاش + بنكك (مع تسجيل رقم العملية).
- بيع هدية مع تغليف ← يُنشئ مهمة في لوحة المغلّف.
- مرتجع/استبدال مرتبط بالفاتورة الأصلية (مع سياسة منع إرجاع العطور/التجميل المفتوحة).
- **الورديات:** فتح بعهدة نقدية ← إغلاق بعدّ النقدية ومطابقة تحويلات بنكك ← تقرير العجز/الزيادة.
- إيصال: طابعة حرارية 80mm أو رابط إيصال عبر واتساب.

### 4.6 العملاء (CRM خفيف)

- المعرّف الوحيد: رقم الهاتف بصيغة موحدة (+249...).
- سجل مشتريات موحد (محل + أونلاين)، عناوين محفوظة، مناسبات مهمة للعميل ← تذكير تسويقي قبلها بأسبوع.
- شرائح عملاء (جدد، متكررون، خامدون أكثر من 90 يوماً).

### 4.7 المالية

- حسابات نقدية: الصندوق، حساب بنكك، عهدة المندوب (COD).
- مصروفات بتصنيفات (إيجار، كهرباء، وقود مولد، رواتب، تسويق) مع مرفقات.
- قائمة دخل مبسطة: المبيعات − تكلفة البضاعة − المصروفات = صافي الربح.
- تصدير CSV/Excel للمحاسب. (المحاسبة الكاملة بقيد مزدوج — مرحلة لاحقة إن لزم.)

### 4.8 التقارير ولوحة المؤشرات

- مبيعات اليوم/الشهر حسب القناة (محل/أونلاين/واتساب)، هامش الربح حسب التصنيف.
- الأصناف الأكثر مبيعاً والراكدة (لم تُبع خلال 60 يوماً).
- قيمة المخزون بالتكلفة، نواقص تحت حد إعادة الطلب، قريبة الانتهاء.
- أداء الموظفين (مبيعات كل كاشير، هدايا كل مغلّف).

### 4.9 المستخدمون والصلاحيات

| الدور | الصلاحيات |
|---|---|
| المالك | كل شيء + التكاليف والأرباح + الإعدادات |
| المدير | المشتريات، المخزون، الأسعار، تأكيد دفعات بنكك، التقارير |
| الكاشير | POS، الوردية، إنشاء عملاء — **لا يرى التكلفة** |
| المغلّف | لوحة التغليف ورفع الصور |
| المندوب | طلبات التوصيل المسندة له، تأكيد التسليم والتحصيل |

## 5. المتجر الإلكتروني

### 5.1 الصفحات

| الصفحة | المحتوى |
|---|---|
| الرئيسية | بانر الموسم (عيد، زواج، تخرج)، تسوق حسب المناسبة، حسب المُهدى إليه، الأكثر مبيعاً |
| التصنيف/البحث | فلترة بالسعر والمناسبة والمقاس واللون، بحث عربي يتجاهل الهمزات والتشكيل |
| المنتج | صور، متغيرات، حالة توفر، خيار "غلّفها كهدية" |
| **صمّم هديتك** | خطوات: اختر المنتجات ← التغليف ← البطاقة ← بيانات المستلم والموعد، مع سعر محدّث لحظياً |
| السلة وإتمام الطلب | صفحة واحدة، دون تسجيل إلزامي |
| تتبع الطلب | برقم الطلب + الهاتف، مع رفع إشعار بنكك إن لم يُرفع |
| صفحات ثابتة | من نحن، سياسة الاستبدال، مناطق ورسوم التوصيل، تواصل |

### 5.2 طرق إتمام الطلب

| الطريقة | المسار | حالة المخزون |
|---|---|---|
| **بنكك** | العميل يرى رقم حساب المحل + المبلغ + رقم الطلب كمرجع ← يحوّل ← يرفع صورة الإشعار + رقم العملية ← المدير يطابق مع كشف الحساب ويؤكد | محجوز حتى التأكيد، يُلغى الحجز بعد المهلة |
| **الدفع عند الاستلام** | تأكيد هاتفي/واتساب للطلبات فوق حد معيّن ← تسليم للمندوب ← تحصيل وتسوية عهدة المندوب | محجوز ← يُخصم عند الخروج للتوصيل |
| **واتساب** | زر "اطلب عبر واتساب" يُنشئ طلباً بحالة `مسودة` ثم يفتح wa.me برسالة جاهزة تحوي رقم الطلب والأصناف | لا حجز حتى يحوّله الموظف لـ `مؤكد` |
| **استلام من المحل** | إتمام ← إشعار "جاهز للاستلام" ← الدفع بالمحل عبر POS برقم الطلب | محجوز ← يُخصم عند التسليم |

> **لماذا يُنشأ طلب في النظام حتى في مسار واتساب؟** حتى لا تضيع الطلبات في المحادثات، ولتبقى التقارير وسجل العميل كاملين.

### 5.3 التوصيل

- مناطق توصيل (أحياء مجمّعة) لكل منطقة رسم ومدة تقديرية — قابلة للتعديل من اللوحة.
- فترات تسليم (Time Slots) بسعة محدودة — مهمة للهدايا المرتبطة بمناسبة.
- خيار "الهدية مفاجأة": إخفاء السعر من الفاتورة المرفقة والتواصل مع المستلم دون ذكر المرسل إلا بإذنه.
- شركات توصيل خارجية لاحقاً عبر نفس واجهة `DeliveryProvider`.

### 5.4 تسويق ومحركات بحث

- أكواد خصم (نسبة/مبلغ، حد أدنى، عدد استخدامات، تاريخ انتهاء).
- كتالوج لمنصات Meta (فيسبوك/إنستغرام) يُولّد تلقائياً (Product Feed) — القناة الأهم للسوق السوداني.
- SEO عربي: روابط واضحة، بيانات منظمة (Product schema)، Sitemap، Open Graph لمشاركة واتساب.

### 6.2 قرارات تصميمية مهمة

1. **جدول `orders` واحد لكل القنوات** مع حقل `channel` (`pos` | `web` | `whatsapp`) — تقارير موحدة ومنطق مرتجعات واحد.
2. **المخزون دفتر حركات:** `stock_movements(variant_id, warehouse_id, batch_id, qty ±, unit_cost, ref_type, ref_id)`، والرصيد الحالي في جدول `stock_levels` يُحدَّث داخل نفس المعاملة (انظر 13.2).
3. **الأسعار تُنسخ إلى سطر الطلب** (`unit_price`, `unit_cost` وقت البيع) — تغيير الأسعار لاحقاً لا يغيّر أرباح الماضي.
4. **المبالغ:** `NUMERIC(14,2)` بالجنيه السوداني، مع حفظ العملة الأصلية وسعر الصرف في مستندات الشراء. لا استخدام Float إطلاقاً.
5. **معرّفات UUID (v7)** متولدة من العميل — ضرورية لإنشاء فواتير POS دون اتصال دون تعارض، مع رقم فاتورة مقروء لكل جهاز (`POS1-000123`).
6. **`branch_id` في كل جدول تشغيلي** من الآن لدعم التوسع.
7. **حذف منطقي (Soft Delete)** للمنتجات والعملاء، ومستندات مالية غير قابلة للحذف (تُلغى بمستند عكسي).

### 6.3 مثال: جداول الطلب الأساسية

```sql
CREATE TABLE orders (
  id              UUID PRIMARY KEY,
  number          TEXT UNIQUE NOT NULL,          -- GHS-2026-000123 / POS1-000045
  branch_id       UUID NOT NULL REFERENCES branches(id),
  channel         TEXT NOT NULL CHECK (channel IN ('pos','web','whatsapp')),
  customer_id     UUID REFERENCES customers(id),
  status          TEXT NOT NULL,                 -- draft|pending_payment|confirmed|wrapping|ready|out_for_delivery|delivered|completed|cancelled
  fulfillment     TEXT NOT NULL,                 -- instore|pickup|delivery
  subtotal        NUMERIC(14,2) NOT NULL,
  discount_total  NUMERIC(14,2) NOT NULL DEFAULT 0,
  wrap_total      NUMERIC(14,2) NOT NULL DEFAULT 0,
  delivery_fee    NUMERIC(14,2) NOT NULL DEFAULT 0,
  grand_total     NUMERIC(14,2) NOT NULL,
  paid_total      NUMERIC(14,2) NOT NULL DEFAULT 0,
  delivery_slot_id UUID REFERENCES delivery_slots(id),
  notes           TEXT,
  created_by      UUID REFERENCES users(id),
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE payments (
  id            UUID PRIMARY KEY,
  order_id      UUID NOT NULL REFERENCES orders(id),
  method        TEXT NOT NULL CHECK (method IN ('cash','bankak','cod')),
  amount        NUMERIC(14,2) NOT NULL,
  status        TEXT NOT NULL,                   -- pending_review|confirmed|rejected
  reference     TEXT,                            -- Bankak transaction no.
  proof_url     TEXT,                            -- receipt image
  confirmed_by  UUID REFERENCES users(id),
  confirmed_at  TIMESTAMPTZ,
  UNIQUE (method, reference)                     -- prevents reusing the same receipt
);
```

> القيد `UNIQUE (method, reference)` يسد ثغرة احتيال شائعة: إرسال نفس إشعار بنكك لأكثر من طلب.

## 7. دورات العمل الرئيسية

### 7.1 حالات الطلب (State Machine)

```
draft -> pending_payment -> confirmed -> wrapping -> ready -+-> out_for_delivery -> delivered -> completed
  |            |               |                            +-> (pickup) -> completed
  +------------+---------------+--> cancelled  (release reservation / restock)
```

الانتقالات محمية في الخلفية (لا يمكن القفز من `pending_payment` إلى `delivered`)، وكل انتقال يُسجّل في `order_status_history` ويرسل إشعار واتساب للعميل عند النقاط المهمة. طلبات POS العادية تنتقل مباشرة إلى `completed`.

### 7.2 بيع في المحل

1. الكاشير يمسح الأصناف ← يضيف العميل برقم الهاتف (اختياري).
2. إن طلب العميل تغليفاً ← يختار نمط التغليف (يُضاف كسطر خدمة).
3. الدفع (كاش/بنكك/مجزأ) ← حفظ محلي فوري في IndexedDB ← إيصال.
4. المزامنة للخادم: معاملة واحدة تُنشئ الطلب + حركات المخزون (بما فيها مواد التغليف) + الدفعات + حركة الصندوق.
5. إن كان هناك تغليف ← مهمة تظهر في لوحة المغلّف.

### 7.3 طلب أونلاين ببنكك

1. العميل يكمل الطلب ← `pending_payment` + حجز المخزون 24 ساعة.
2. يحوّل ويرفع الإشعار + رقم العملية ← `payment.status = pending_review` + تنبيه للمدير.
3. المدير يطابق مع تطبيق بنكك ← تأكيد ← `confirmed` + رسالة واتساب للعميل.
4. التغليف ← صورة الهدية للعميل ← توصيل ← تأكيد المندوب.
5. إن انتهت المهلة دون دفع ← إلغاء تلقائي وفك الحجز (مهمة مجدولة كل 15 دقيقة).

### 7.4 استلام شحنة بضاعة

1. أمر شراء بعملة المورد (مثلاً درهم).
2. استلام الكميات الفعلية + تواريخ الصلاحية ← طباعة ملصقات باركود.
3. إدخال مصاريف الشحنة ← توزيعها ← تكلفة وصول بالجنيه بسعر صرف اليوم.
4. تحديث متوسط التكلفة ← اقتراح أسعار بيع جديدة ← المالك يعتمد.
5. الأصناف تظهر في المتجر تلقائياً إن كانت مفعّلة للويب.

### 7.5 هدية مخصصة بموعد محدد

1. العميل يبني الهدية ويحدد الموعد ← النظام يتحقق من سعة الفترة ومن مهلة التجهيز (مثلاً 3 ساعات كحد أدنى).
2. بعد التأكيد، المهمة تظهر للمغلّف مرتبة حسب "آخر وقت لبدء التجهيز".
3. المغلّف يستهلك المواد (تُخصم تلقائياً حسب النمط، مع إمكانية تعديل الفعلي) ← يرفع صورة ← `ready`.
4. بطاقة الإهداء تُطبع من النظام بقالب غصن.

## 8. الأمان، النسخ الاحتياطي، والعمل دون إنترنت

### 8.1 استراتيجية العمل دون اتصال (POS)

- عند بدء الوردية: تحميل الكتالوج والأسعار والعملاء المتكررين ولقطة المخزون إلى IndexedDB.
- البيع يُحفظ محلياً في **طابور صادر (Outbox)** مع مفتاح عدم تكرار (Idempotency Key = UUID الطلب) ← إعادة الإرسال آمنة ولا تُنشئ فاتورة مكررة.
- مؤشر واضح للكاشير: متصل / غير متصل (عدد الفواتير المعلّقة).
- **تعارض المخزون:** إن بيع آخر قطعة في المحل وأونلاين في نفس الوقت، بيع المحل يُقبل دائماً (البضاعة خرجت فعلاً) ويُسمح برصيد سالب مؤقت مع تنبيه، والطلب الأونلاين يُوضع في انتظار مع تواصل مع العميل.
- للمنتجات ذات الرصيد المنخفض يمكن تخصيص "مخزون أمان" لا يُعرض أونلاين.

### 8.2 الأمان

- HTTPS إلزامي عبر Cloudflare، تجزئة كلمات المرور بـ Argon2، جلسات موظفين محدودة بالجهاز.
- الصلاحيات تُفحص في الخلفية لكل عملية (ليس بإخفاء الأزرار فقط).
- تحديد معدل الطلبات (Rate Limiting) على إتمام الطلب ورفع الإشعارات وتتبع الطلبات لمنع الطلبات الوهمية.
- صور الإشعارات في حاوية خاصة (روابط موقّعة مؤقتة)، ليست عامة.
- سجل تدقيق (`audit_log`) لتغيير الأسعار، الخصومات الكبيرة، تعديل المخزون، تأكيد/رفض الدفعات، إلغاء الفواتير.
- تحقق ثنائي (2FA) لحساب المالك والمدير.

### 8.3 النسخ الاحتياطي

| النوع | التكرار | الوجهة | الاحتفاظ |
|---|---|---|---|
| pg_dump كامل | يومياً | Cloudflare R2 / Backblaze B2 (مزود مختلف عن الخادم) | 30 يوماً + شهري لسنة |
| WAL / PITR | مستمر (اختياري مرحلة 2) | نفس الوجهة | 7 أيام |
| الصور | تزامن أسبوعي | حاوية ثانية | دائم |

- **اختبار استعادة شهري** — النسخة التي لم تُختبر استعادتها ليست نسخة احتياطية.
- تصدير Excel يومي تلقائي للمبيعات والمخزون إلى بريد المالك كطبقة أمان إضافية.
- مراقبة توفر (Uptime Kuma أو Better Stack المجاني) مع تنبيه عبر تيليجرام/بريد.

## 11. تطبيقات الجوال

### 11.1 القرار: تطبيقان فوق نفس الخلفية

| التطبيق | المستخدمون | الوظائف الأساسية |
|---|---|---|
| **تطبيق غصن للعملاء** | العملاء | تصفح وبحث، صمّم هديتك، سلة وإتمام طلب، رفع إشعار بنكك من معرض الصور، تتبع الطلب، إشعارات فورية، عناوين محفوظة، إعادة طلب سابق، تذكير بالمناسبات، نقاط الولاء |
| **تطبيق غصن للموظفين** | المالك، المدير، المغلّف، المندوب | واجهة حسب الدور (تفاصيلها في 11.2) |

**لماذا تطبيقان وليس تطبيقاً واحداً؟** تطبيق العملاء يُنشر للعامة في المتجر، بينما تطبيق الموظفين فيه صلاحيات حساسة (التكاليف، تأكيد الدفعات) ويُوزّع داخلياً فقط. فصلهما يقلل سطح الهجوم ويُبقي تطبيق العملاء خفيفاً. الكود المشترك (الواجهات، التحقق، الترجمة، عميل الـAPI) في حزم مشتركة داخل نفس المستودع.

**نقطة البيع (POS) تبقى تطبيق ويب (PWA) على الجهاز اللوحي** — لا حاجة لإعادة بنائها في تطبيق أصلي، ويمكن ضمها لتطبيق الموظفين لاحقاً إن لزم.

### 11.2 تطبيق الموظفين حسب الدور

| الدور | الشاشات |
|---|---|
| المالك | لوحة مؤشرات اليوم (مبيعات، أرباح، طلبات معلقة)، تنبيهات (نواقص، قرب انتهاء، فروقات وردية)، اعتماد الأسعار المقترحة |
| المدير | **مراجعة دفعات بنكك** (صورة الإشعار + المبلغ + رقم العملية ← تأكيد/رفض بضغطة)، استلام بضاعة، جرد بمسح الباركود بالكاميرا، إدارة الطلبات |
| المغلّف | قائمة مهام التغليف حسب الموعد، تفاصيل الهدية ونص البطاقة، تصوير الهدية الجاهزة وإرسالها للعميل |
| المندوب | الطلبات المسندة، فتح الموقع في الخرائط، اتصال/واتساب بالعميل، تأكيد التسليم بصورة، تسجيل التحصيل النقدي (COD)، يعمل دون اتصال ويزامن لاحقاً |

| الطبقة | الاختيار | السبب |
|---|---|---|
| إطار التطبيق | **Expo (React Native) + TypeScript** | نفس لغة الويب، كود واحد لأندرويد وiOS، مطوّر واحد يديره |
| هيكل المستودع | Turborepo: `apps/web` (Next.js) · `apps/customer` · `apps/staff` · `packages/api-client` · `packages/validation` (Zod) · `packages/i18n` | مشاركة المنطق وقواعد التحقق بين الويب والجوال |
| عقد الـAPI | **REST بإصدارات (`/api/v1`) + OpenAPI** يولّد عميلاً مكتوب الأنواع | التطبيقات المثبتة عند المستخدمين تعمل بإصدارات قديمة؛ الإصدارات تحمي من كسرها عند تحديث الخادم |
| المصادقة | Access Token قصير + Refresh Token في `SecureStore`؛ العملاء بـ OTP، الموظفون بكلمة مرور + ربط بالجهاز | آمن وقابل للإلغاء عن بُعد عند فقدان جهاز موظف |
| التخزين المحلي | `expo-sqlite` لتطبيق الموظفين (مندوب، جرد)، كاش للكتالوج في تطبيق العملاء | العمل مع انقطاع الشبكة |
| الإشعارات | Expo Notifications (FCM/APNs) + واتساب كقناة احتياطية | الإشعار الفوري قد لا يصل دائماً — واتساب يضمن الوصول |
| التحديثات | **EAS Update (OTA)** | إصلاح الأخطاء فوراً دون انتظار مراجعة المتجر — مهم لمطوّر واحد |
| الواجهة | `I18nManager.forceRTL` + خطوط عربية مضمّنة | اتجاه عربي صحيح على كل الأجهزة |

### 11.4 إضافات قاعدة البيانات

- `devices` — رموز الإشعارات لكل مستخدم/جهاز، المنصة، إصدار التطبيق.
- `refresh_tokens` — جلسات قابلة للإلغاء.
- `notifications` — سجل الإشعارات المرسلة وحالتها.
- `app_versions` — أقل إصدار مدعوم لكل تطبيق ← إجبار التحديث عند تغيير غير متوافق.

### 11.5 التوزيع (يحتاج تحقق)

1. **أندرويد أولاً** — الشريحة الأكبر في السوق السوداني غالباً. تطبيق العملاء على Google Play بحساب مطوّر من قطر (رسوم لمرة واحدة).
2. **تطبيق الموظفين:** توزيع داخلي (Play Internal Testing أو ملف APK مباشر) — لا يُنشر للعامة.
3. **iOS:** توفر App Store وخدمات Apple في السوق السوداني **غير مؤكد ويحتاج تحقق**؛ مستخدمو آيفون يستخدمون المتجر كـPWA (إضافة للشاشة الرئيسية) حتى يُحسم الأمر.
4. **الإشعارات عبر FCM:** توفر خدمات Google في السودان يحتاج اختباراً فعلياً على أجهزة هناك؛ لذلك واتساب يبقى القناة المضمونة للإشعارات المهمة.
5. حجم التطبيق صغير (هدف أقل من 30MB) ويعمل على أجهزة أندرويد متوسطة ومنخفضة المواصفات.

### 11.6 موقع التطبيقات في خطة التنفيذ

| المرحلة | المخرجات | المدة التقديرية |
|---|---|---|
| ضمن المرحلة 1–2 | تصميم الـAPI بإصدارات من البداية (حتى لا يُعاد بناؤه لاحقاً) | بدون مدة إضافية تقريباً |
| **2ب — تطبيق الموظفين** | مراجعة دفعات بنكك، لوحة المالك، مهام المغلّف، تطبيق المندوب مع Offline | 2–3 أسابيع |
| **3ب — تطبيق العملاء** | الكتالوج، صمّم هديتك، الطلب والدفع، التتبع، الإشعارات | 3–4 أسابيع |

> **لماذا تطبيق الموظفين قبل تطبيق العملاء؟** يحقق فائدة تشغيلية من اليوم الأول (تأكيد الدفعات والتوصيل من أي مكان، وأنت تدير من قطر)، بينما العملاء في البداية يصلون عبر المتجر ووسائل التواصل. تطبيق العملاء يصبح مجدياً بعد تكوّن قاعدة عملاء متكررين.

**تكاليف إضافية تقريبية:** حساب Google Play (~25 دولار لمرة واحدة)، حساب Apple Developer (~99 دولار سنوياً عند تفعيل iOS)، خطة EAS المجانية كافية غالباً في البداية.

## 12. وحدة رسائل واتساب (WhatsApp Business API)

**القرار:** اعتماد WhatsApp Cloud API كقناة التواصل الأساسية مع العملاء، ونقلها من المرحلة 4 إلى **المرحلة 2** (مع إطلاق المتجر).

### 12.1 المعمارية

- طبقة `MessagingProvider` موحدة: كل رسائل النظام تمر عبرها ← يمكن التبديل بين Meta Cloud API مباشرة أو وسيط معتمد (BSP مثل 360dialog / Twilio) دون تعديل منطق النظام.
- **طابور إرسال (Queue)** مع إعادة محاولة تلقائية عند الفشل، وقناة احتياطية (SMS أو رابط `wa.me` يدوي للموظف).
- **Webhook** لاستقبال حالات الرسائل (أُرسلت / وصلت / قُرئت / فشلت) ورسائل العملاء الواردة.

### 12.2 الرسائل التلقائية (قوالب معتمدة من Meta)

| الحدث | الرسالة | النوع |
|---|---|---|
| إنشاء الطلب | تأكيد الاستلام + رقم الطلب + رابط التتبع | خدمية |
| مراجعة دفعة بنكك | تأكيد الدفع أو رفضه مع السبب | خدمية |
| بدء التجهيز | الهدية قيد التجهيز | خدمية |
| جاهز | صورة الهدية الجاهزة + موعد التسليم أو الاستلام | خدمية |
| خروج للتوصيل | اسم المندوب ورقمه | خدمية |
| تم التسليم | شكر + طلب تقييم | خدمية |
| رمز الدخول | OTP لتطبيق العملاء والمتجر | مصادقة |
| مناسبة العميل | تذكير قبل أسبوع + عرض | تسويقية (بموافقة) |
| سلة متروكة | تذكير بعد 24 ساعة | تسويقية (بموافقة) |
| إشعارات داخلية | دفعة بنكك جديدة للمدير، نواقص مخزون للمالك | خدمية |

### 12.3 صندوق الوارد (Inbox)

- محادثات العملاء تظهر في لوحة الإدارة وتطبيق الموظفين، مرتبطة بسجل العميل وطلباته.
- إسناد المحادثة لموظف، ردود جاهزة، وتحويل المحادثة إلى طلب بضغطة.
- الرد المجاني/الأرخص داخل نافذة الـ24 ساعة بعد رسالة العميل.

### 12.4 قاعدة البيانات

- `message_templates` — القوالب ونصوصها ولغتها وحالة اعتمادها من Meta.
- `message_log` — كل رسالة: المستلم، القالب، الحالة، التكلفة، المرجع (طلب/دفعة).
- `customer_consents` — موافقة العميل على الرسائل التسويقية وتاريخها ومصدرها.
- `conversations` و`conversation_messages` — صندوق الوارد.

### 12.5 متطلبات الإعداد (تبدأ فوراً لأنها تستغرق وقتاً)

1. حساب Meta Business Manager وتوثيق النشاط التجاري.
2. رقم هاتف مخصص للـAPI (لا يُستخدم في تطبيق واتساب العادي في نفس الوقت).
3. تسجيل القوالب واعتمادها من Meta قبل الإطلاق.
4. **يحتاج تحقق:** إمكانية تسجيل رقم سوداني (+249) وتوثيق نشاط في السودان على WhatsApp Business Platform. البديل: التسجيل برقم ونشاط من قطر.
5. **التكلفة:** تُحاسب رسائل القوالب حسب الفئة (تسويقية / خدمية / مصادقة) ودولة المستلم — تحقق من جدول أسعار Meta الحالي. ضع سقفاً شهرياً للرسائل التسويقية في الإعدادات.

## 13. قابلية التوسع والأداء

**الخلاصة:** البنية مناسبة لعشرات الآلاف من المنتجات — هذا حجم صغير لـ PostgreSQL. نقاط الضغط الحقيقية هي البحث والعرض والمزامنة، وليست حجم قاعدة البيانات.

### 13.1 تقدير الأحجام (سيناريو 50,000 منتج)

| البند | الحجم التقريبي | التقييم |
|---|---|---|
| المنتجات والمتغيرات | 50 ألف منتج ← 100–150 ألف متغير | صغير جداً |
| حركات المخزون | 500 عملية بيع يومياً × 3 أصناف ← ~550 ألف سجل سنوياً | طبيعي |
| حجم قاعدة البيانات | أقل من 5GB لسنوات | صغير |
| الصور | 50 ألف × 4 صور × عدة مقاسات ← ~30–60GB | تكلفة R2 حوالي 1 دولار شهرياً |

### 13.2 التعديلات المعتمدة

1. **البحث بالعربي:** PostgreSQL Full-Text Search + `pg_trgm` لتحمّل الأخطاء الإملائية، مع عمود مُطبَّع (توحيد الهمزات والتاء المربوطة وإزالة التشكيل). الانتقال إلى **Meilisearch** على نفس الخادم عند الحاجة لبحث فوري بفلاتر متعددة أو تجاوز ~100 ألف متغير.
2. **المتجر:** صفحات المنتجات والتصنيفات تُبنى مسبقاً وتُحدَّث عند التعديل (ISR) وتُخزَّن في Cloudflare؛ القوائم بصفحات متتالية (Cursor Pagination).
3. **نقطة البيع دون إنترنت:** تحميل نسخة خفيفة من الكتالوج فقط (الاسم، الباركود، السعر، الرصيد — ~10–20MB لـ 50 ألف منتج)، ومزامنة التغييرات فقط حسب `updated_at`، والصور تُحمَّل عند الحاجة وتُحفظ على الجهاز.
4. **رصيد المخزون:** جدول `stock_levels` يُحدَّث داخل نفس معاملة الحركة (يحسم الخيار المفتوح في 6.2).
5. **لوحة الإدارة:** التصفية والتقسيم لصفحات على الخادم، والتصدير الكبير كمهمة خلفية.
6. **الاستيراد الجماعي:** مهمة خلفية تعالج الملف على دفعات مع تقرير أخطاء بدل فشل الملف كاملاً.
7. **الفهارس:** فهرس فريد على الباركود والـSKU، وفهارس على التصنيف والحالة وتاريخ التعديل، وفهرس trigram للبحث.

### 13.3 الخادم ومسار النمو

| المرحلة | الخادم |
|---|---|
| الإطلاق | VPS بـ 4 vCPU و8GB RAM (يستوعب التطبيق وPostgreSQL وMeilisearch والمهام الخلفية) |
| نمو الزيارات | ترقية نفس الخادم (Vertical Scaling) |
| نمو كبير (عدة فروع أو بيع النظام لمحلات أخرى) | فصل قاعدة البيانات على خادم مستقل أو خدمة مُدارة، وتشغيل أكثر من نسخة من التطبيق خلف موازن أحمال |

> **ملاحظة:** الذي يحدد حجم الخادم هو عدد الزوار المتزامنين وليس عدد المنتجات. خادم بهذا المستوى مع تخزين Cloudflare يستوعب عادةً مئات المستخدمين المتزامنين — تقدير عام يُحسم باختبار تحميل (k6) قبل الإطلاق. تكلفة الخادم الأكبر ترفع التقدير في 9.2 بفارق بسيط (عدة دولارات شهرياً).
